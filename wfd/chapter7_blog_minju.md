# 7장 기술 블로그 쉽게 쓰고 운영하기

## 01 기술 블로그를 쉽게 쓰는 방법 3가지

### 개발자가 기술 블로그를 잘 못 쓰는 이유

- 학교에서 배운 글쓰기 방식(논설문, 설명문)은 목적이 분명해야 쓸 수 있는 방식임.
- 개발자의 글쓰기는 **주제 의식**이 아니라 **소재 의식**에 가까움.
  - 개발기는 논설문이 아니라 그저 개발 과정 그 자체를 말하는 것임.
  - 블로그 독자 수준이 천차만별이므로 '초등학생도 이해할 수 있는 수준'으로 쓰는 개발자는 없음.
- 방법: 소재 우선 글쓰기, 자기 수준 글쓰기, 재미있는 글쓰기

### 첫째, 주제 의식을 버리고 소재 의식으로 쓰자

- **주제 의식**: 민족, 자존감, 자본주의 같은 추상적 가치 기반
- **소재 의식**: 특정 대상이나 상황에 대한 자기만의 관점, 해결 방안

> 기술 블로그는 수필이나 에피소드와 비슷함.
> "데이터베이스의 자동증가 값을 기본키로 사용할 수 없을 때?" 같은 글이 바로 소재 의식임.

### 둘째, 독자 수준이 아니라 자기 수준으로 쓰자

- 기술 용어를 무조건 풀어 쓰거나 쉬운 용어로 바꿀 필요 없음.
- 독자가 모르는 용어는 **위키피디아 링크**로 대체하는 편이 나음.

```
[잘못된 예]
반응형 웹을 만들 때 CSS를 잘 활용해야 합니다.
CSS(Cascading Style Sheets)는 마크업 언어가 실제 표시되는 방법을 기술하는 언어로...
(본문보다 CSS 설명이 더 길어짐)

[좋은 예]
반응형 웹을 만들 때는 CSS(https://ko.wikipedia.org/wiki/CSS)를 잘 활용해야 합니다.
```

- 기술 블로그는 **실력이 비슷한 독자**를 위한 것임.
- 핵심만 쓰고 나머지는 독자가 공부할 수 있도록 **길만 터놓는 것**이 현명한 방법임.

### 셋째, 재미있게 글을 쓰자

- 글쓰기 기교는 글을 아름답고 쉽게 읽히게 함 → 독자 반응 증가 → 글 쓸 동력 확보 (**선순환**)
- 경험과 기교가 없는 글은 재미가 없어서 블로그가 오래가지 못함.

| 구분 | 특징 |
|---|---|
| 위키피디아 스타일 | 정확하지만 재미없음 |
| 나무위키 스타일 | 경험과 기교가 있어 읽는 재미가 있음 |

## 02 글의 종류별로 목차 잡는 법 I - 저술

### 기술 블로그의 4종류, 저, 술, 편, 집

| 구분 | 내용 | 종류 |
|---|---|---|
| 저 | 직접 경험하고 실험한 과정이나 결과 | 개발기, 도입기, 적용기 |
| 술 | 어떤 것을 분석하여 의미를 풀이하고 해석한 것 | 기술 소개, 용어 분석, 에러 해결 방법 등 |
| 편 | 산만하고 복잡한 자료를 편집해 질서를 부여한 것 | 프로그램 설치/설정 방법, 튜토리얼, 세미나 후기, 책 리뷰 |
| 집 | 여러 사람의 견해나 흩어진 자료를 한데 모아 정리한 것 | 명령어 모음, 팁, OO가지 규칙 |

### 저: 개발기는 목차를 잘 잡아서 본문부터 쓰자

- 저는 직접 경험한 것을 쓴 것임.
- 개발기 목차는 **1차원 단방향**이지만 개발자의 경험은 **2차원 양방향**임.
- 2차원 양방향 경험을 1차원 단방향 목차로 바꾸는 핵심 방법: **최종 성공 루트와 중간 실패 루트를 구별**하는 것.

```
경험 루트: A → B → C → D → E → F → G → H → I
최종 루트: A → D → I
문제해결/팁 루트: A → B → C → A, E → F → G → H
```

- 목차를 정했으면 **머리말부터 쓰지 말고 본문부터** 쓰자.
  - 머리말(서비스 설명, 개발의 필요성)은 개발자에게 익숙하지 않은 글임.
  - 개발이 완료되면 아키텍처, 알고리즘, 모델, 플로우 같은 산출물이 나오므로 그 이미지를 먼저 붙이고 쓰면 단번에 몇 단락을 쓸 수 있음.
  - **본문 → 맺음말 → 머리말** 순서로 쓰는 것이 효율적임.

### 술: 원전을 비교하고 실험해 풀이해서 쓰자

- 술은 어떤 것을 분석해 의미를 풀이하고 해석한 것임.
- 개발에서 원전은 스펙 문서, 프로토콜, 레퍼런스임.
- **원전의 내용을 먼저 쓰고 비교한 내용을 추가**하는 것만으로 기술 블로그를 쉽게 쓸 수 있음.

```
술에 해당하는 글 예시
- GET과 POST의 차이
- MySQL Ascending index vs. Descending index
- Webpack 4의 Tree Shaking에 대한 이해
- MySQL 1175 에러 해결 방안
```

- 원전의 내용을 직접 실험해 비교한 뒤 결과를 정리해 풀이할 수도 있음.
  - 기업에서는 서비스 성능을 높이기 위해 여러 가지 실험을 많이 하므로 그 결과를 잘 정리하기만 해도 좋은 글이 됨.

## 03 글의 종류별로 목차 잡는 법 II - 편집

### 편: 순서를 요약하여 쓰자

- 편은 산만하고 복잡한 자료를 편집해 질서를 부여한 것임.
- 시간 순서로 일어난 일이나 해야 할 일을 쓴 것: 프로그램 설치/설정 순서, 튜토리얼, 개발자 컨퍼런스 후기 등.
- **쓰는 방법**: 한 일을 시간 순서로 나열 → 단계로 묶어서 요약 → H2 태그 적용으로 목차 완성.

```
[단계로 묶기 전]
- 가까운 지하철로 간다.
- 지하철 2호선을 타고 사당역으로 간다.
- 4호선으로 갈아타고 서울역으로 간다.
- 부산KTX역으로 가는 KTX 기차표를 끊는다.
...

[단계로 묶은 후 목차]
1. 강남에서 서울KTX역으로 가기
   가. 가까운 지하철로 간다.
   나. 지하철 2호선을 타고 사당역으로 간다.
   다. 4호선으로 갈아타고 서울역으로 간다.
2. KTX를 타고 부산으로 가기
   ...
```

- 글쓰기에 능숙하지 않다면 구조를 생각하지 말고 본인이 한 일을 쭉 나열하고, 그 내용부터 쓴 다음 단계로 묶으면서 요약하자.

### 집: 글쓰기가 두렵다면 자료를 모아 핵심을 엮어서 쓰자

- 집은 여러 사람의 견해나 흩어진 자료를 한데 모아 정리하는 것임.
- 기술 블로그에서는 **명령어 모음, 팁, OO가지 규칙** 같은 것이 집에 해당함.
- 본인이 경험에서 터득한 것을 핵심만 정리해서 나열해도 좋은 집이 될 수 있음.

> 기술 블로그를 처음 쓰는 개발자라면 가장 쉽게 도전할 수 있는 글이 **집**, 그다음이 **편**임.  
> 본인이 이미 알고 있거나 쉽게 찾을 수 있는 자료를 모아서 나열하거나 일정한 순서와 단계로 엮기만 하면 됨.

## 04 기업의 기술 블로그 운영 팁

### 기술 블로그는 회사의 가치를 높인다

기술 블로그를 운영하려는 기업이 늘어나는 이유 3가지:

1. 직무에 적합하면서 개발 능력이 우수한 개발자 채용에 도움을 줌. 구직자가 회사의 개발 문화와 수준을 판단할 수 있음.
2. 개발 과정에서 생긴 노하우를 체계적으로 축적할 수 있음. 문서 관리 체계가 미흡한 스타트업에 특히 유용함.
3. 기술 블로그에 글을 써서 올리려면 지식을 체계화하는 과정이 필요함 → 개발 수준 향상 → 개발자의 몸값 상승.

### 기술 블로그도 투자를 해야 살아난다

- 블로그를 개발자에게만 맡겨 두고 투자를 안 하면 악순환에 빠짐.

```
투자 없음 → 방문자 없음 → 글 읽는 사람 없음 → 반응 없음 → 개발자 글쓰기 포기 → 블로그 유명무실
```

- 기업의 기술 블로그는 **광고 매체**처럼 다뤄야 함.
  - 타깃 독자에게 홍보하고 검색엔진에 잘 검색되게 하고 최신 트렌드를 추적해 태그를 달아야 함.
  - 기술 블로그 운영자가 이런 일을 제대로 할 수 있도록 **필요한 비용을 투자**해야 함.

### 개발자의 글쓰기는 회사의 문화를 반영한다

- 기업의 기술 블로그는 개인 블로그와 달리 **기본 체계와 일정 수준**이 보장돼야 함.
- 글쓰기 원칙이나 수준을 정하기 전에 **회사의 글쓰기 문화**를 먼저 정의해야 함.

| 블로그 | 스타일 특징 |
|---|---|
| 네이버 기술 블로그 | 정형화한 구성, 논문 제목 같은 목차, 세련된 문체, 간결한 표현 (건조하고 딱딱한 느낌) |
| 우아한형제들 기술 블로그 | 자연스러운 표현, 실감 나는 구성, 자극적인 제목, 제약 없는 묘사 (약간 비전문적 느낌) |

### 협업해서 글쓰기, 짝 글쓰기를 해보자

- 개발에 짝 프로그래밍(Pair Programming)이 있듯 글쓰기에도 **짝 글쓰기(Pair Writing)** 가 있음.
- 짝 글쓰기의 장점: 글의 완성도 향상, 지식 보편화, 팀 회고, 심리적 안정감.

| 방식 | 설명 |
|---|---|
| Driver & Navigator | 한 명은 글을 쓰고(Driver) 다른 한 명은 검토(Navigator)하는 방식 |
| Coder & Adviser | 한 명은 글을 쓰고(Coder) 다른 한 명은 조언(Adviser)하는 방식 |
| Verbalizer & Listener | 글을 쓰고 난 뒤 한 명은 글을 읽고(Verbalizer) 다른 한 명은 귀로 듣는(Listener) 방식 |
| Ping-Pong | 두 명이 번갈아 가면서 글을 쓰는 방식 |
